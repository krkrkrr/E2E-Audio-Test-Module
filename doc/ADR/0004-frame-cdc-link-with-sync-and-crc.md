# ADR-0004: CDC の上り方向を同期語と CRC 付きのバイナリフレームにし、下り方向は ASCII の行コマンドにする

## Status

Accepted

## Context

CDC は区切りの無いバイト列である。
その上で、録音データ、セッションの開始と終了、エラー、デバイス情報を運ぶ必要がある（[ADR-0002](0002-stream-capture-over-usb-cdc.md)）。

録音データは 192,000 B/s あり、テキストにすると帯域が数倍になる。
ハーネスは、ポートを開いた時点で途中から読み始めることがある。
以前の MicroPython の出力のような無関係なバイトが残っていることもある。
そのため、受信側がバイト列の途中から区切りを見つけ直せる必要がある。

欠落は、黙って失わずにホストが検出できなければならない。
パケットの連番だと「何フレーム失ったか」が分からないが、音声フレームの位置なら差がそのまま欠落数になる。

ハーネスからデバイスへのコマンドは数種類で、頻度も低い。
serial MCP やターミナルから人が手で打てると、デバッグしやすい。

## Decision

デバイスからハーネスへは、次のバイナリフレームで送る。

`A5 5A` | 種別 u8 | 長さ u16 LE | ペイロード | CRC-16/CCITT-FALSE u16 LE（種別〜ペイロード）

種別は STARTED（0x01）、DATA（0x02）、ENDED（0x03）、INFO（0x04）、ERROR（0x7F）とする。
DATA は先頭の位置（u64）と、1〜256 個の音声フレームを持つ。
欠落は、連続する DATA の位置の飛びと、ENDED の `dropped_frames` で表す。

ハーネスからデバイスへは、`\n` で終わる ASCII の行（`START`、`STOP`、`INFO`）で送る。
`\r` は無視し、32 バイトを超える行は ERROR にする。

## Consequences

- 受信側は `A5 5A` を探し、CRC が合うまで 1 バイトずつずらして同期を取り直せる
- 欠落の位置と量がフレーム単位で分かる
- 人がターミナルからコマンドを打てる。ただし応答はバイナリなので、読むにはハーネスのデコーダが要る
- DATA 1 個あたりのオーバーヘッドは 15 B で、256 フレーム（1,024 B）に対して約 1.5 % になる
- 種別やペイロードを増やすときは、この ADR を置き換える新しい ADR が要る
